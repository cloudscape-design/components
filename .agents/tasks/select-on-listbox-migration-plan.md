# Moving Select and Multiselect onto the OptionList implementation

Read-only investigation. Code read at `.worktrees/fix-listbox-alignment` (branch `fix/select-multiselect-listbox-alignment`, HEAD `f4e7628ca`, which is #5204 + #5180 + #5208 stacked). Nothing was edited, built or run.

## Summary

- **Recommend Route A (engine), done as a shared core hook.** Split `useListbox` into a focus-agnostic core (highlight, navigation, choose guard, mouse handlers, option props, announcement) plus OptionList's inline-focus layer, and build `useSelect` on the same core. `useSelect` keeps only the dropdown shell (open state, trigger, filter, dialog, focus).
- **This has already been prototyped.** Branch `refactor/listbox-unified-core` (`b2f8bf0ec`, worktree `.worktrees/listbox-unified-2`) adds `src/internal/components/listbox/use-listbox-core.ts` (199 lines) and moves OptionList, Select and Multiselect onto it. It changed no test file. Unit (93 suites, 1346 tests), snapshot (111 snapshots) and functional tests (1987) matched before and after (`.agents/tasks/listbox-unified-report.md`). The source it was built on differs from the current stack only in small places (`git diff --stat 866fcb0c1 f4e7628ca` touches `use-select.ts` 0 lines, `select/internal.tsx` 4, `use-multiselect.tsx` 4, `use-listbox.ts` 2, `navigation.ts` 13), so it can be ported rather than rewritten.
- **Route B (Select renders `InternalOptionList`) is viable on paper but needs about 15 internal-only props and an imperative handle.** Select's trigger and filter input drive the highlight from outside the list, including before the list opens. That state would have to be lifted out of `InternalOptionList` again, which is Route A with an extra layer. Using the *public* `OptionList` is not an option: it would count OptionList telemetry inside every Select (`option-list/index.tsx:15`, `useBaseComponent('OptionList')`) and make `createWrapper().findOptionList()` match Select's dropdown.
- **Embedded Multiselect is the one place where reusing OptionList's inline behavior fits.** It is inline, has its own tab stop and stays open (`multiselect/embedded.tsx:68-69`, `use-select.ts:247-254`). Moving it onto OptionList's focus behavior changes what is highlighted on focus, so it is a separate, opt-in PR.

## Route comparison

| | Route A: shared core | Route B: `InternalOptionList` |
|---|---|---|
| Layers | Select → `useSelect` (dropdown shell) → `useListboxCore`. OptionList → `useListbox` (inline focus) → `useListboxCore`. Same `PlainList`/`VirtualList` | Select → `useSelect` shell → `InternalOptionList` → `useListbox` → `Listbox`. Highlight state is inside the list but driven from the trigger and filter through a ref |
| Lines | Measured on the prototype: 8 files, +338/−218 (`use-listbox-core.ts` +199, `use-listbox.ts` 257→196, `use-select.ts` 350→331). Renderer cleanup adds roughly +60/−80 | Estimate: `InternalOptionList` 212 → about 400 (internal props, bypass paths, imperative handle), `useListbox` +80 for options, Select/Multiselect −100 to −150. Net about +350 |
| Internal API added | One internal hook with about 10 options (prototype `UseListboxCoreProps`) | About 15 `__` props on `InternalOptionList` plus an imperative handle (`goHome`, `resetHighlight`, `onKeyDown`, `highlightedId`, raw setters) |
| DOM, classes, test-utils, snapshots | No DOM change. Prototype: snapshot and functional tests identical | Adds the OptionList root div and test classes unless suppressed. Risk to `findOptionList()`, the first row's top divider, and the test-utils selector snapshot |
| Coupling | Select and OptionList depend on a neutral internal hook | Select depends on another component's internals, and OptionList gains Select-only modes that its own tests don't cover |
| Effort | Port 3 existing commits, resolve small conflicts, then optional follow-ups | New design: lift state through refs, handle open/closed lifetimes, add internal prop tests |
| Risk to Select / Multiselect / PropertyFilter | Low. Logic moves, `useSelect`'s returned API stays, so `use-select.test.ts` (498 lines) and all component tests run unchanged | Medium to high. Timing changes from ref-driven highlight before open, scroll semantics differ (`scrollRequest` vs `highlightedIndex`), embedded Multiselect focus differs |

**Recommendation: Route A.** The three strongest reasons:

1. Select's highlight is driven from outside the list, before and while it opens (`use-select.ts:174-177`, `:210-230`, `:273-296`). Route B would have to lift that state back out through a ref, which rebuilds Route A behind an extra layer.
2. Route A needs no DOM or test-utils change, and that has been shown: the prototype changed no test and kept snapshot and functional tests identical. Route B adds a root wrapper, test classes and a missing top divider that must each be switched off.
3. Route A keeps OptionList's public layer thin (`toInternalOptions`, `useControllable`, value warning, `renderOption` mapping) and free of Select-only modes. Route B makes OptionList the most coupled component in the family.

Route B makes sense in one case: moving the embedded Multiselect onto OptionList's inline focus behavior. Even there, using the `useListbox` hook (Route A, PR 4 below) gets the same result without the `InternalOptionList` props.

## Open decisions

- Route A as recommended, by porting the prototype commits (`45567f02d`, `1b0f891c9`, `b2f8bf0ec`) rather than rewriting?
- Is one PR for Select and Multiselect (PR 3) acceptable? A Select-only first step would need a temporary second copy of `useSelect`.
- Do PR 4 (Select renders `Listbox`, `VirtualList` moves into `listbox/parts`)? It removes the most duplicated wiring but carries the scroll risk.
- Should the embedded Multiselect (PropertyFilter) adopt OptionList's focus highlight (PR 5)? It changes behavior and needs an accessibility review.
- Keep the different highlight-on-open rule (Select: selection order; OptionList: list order)? This plan keeps it.
- Unify scroll triggering later (Select on `highlightedIndex`, OptionList on `scrollRequest`)? This plan keeps both.
- Run the test dedup after the migration (recommended) or before?
- Autosuggest stays out of scope (it has its own list in `src/autosuggest/plain-list.tsx` and `virtual-list.tsx`).
